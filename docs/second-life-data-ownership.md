# セカンドライフのデータ所有ルール

## 目的

セカンドライフの設計内容と、住まい・生活費・ライフイベントに存在する計算用データが別々に編集され、内容が食い違うことを防ぐ。

## 基本原則

### 1. `SecondLifeState` が「設計」の本体

セカンドライフでユーザーが決める意思・シナリオは `SecondLifeState` を正とする。

例:

- セカンドライフ開始年齢
- 住み続ける / 地元へ戻る / 新しい土地へ移る
- リフォーム / 購入 / 賃貸
- セカンドライフ期の生活水準
- 世帯主・配偶者それぞれの介護開始年齢、介護形態、介護費

同じ設計情報を別画面で独立して持たない。

### 2. 各入力画面は「詳細入力」と「計算用反映先」

住まい・生活費・ライフイベントは、それぞれのドメインの通常入力を管理する。

セカンドライフから生成されたデータについては、設計の本体ではなくキャッシュフロー計算へつなぐ projection（反映データ）として扱う。

### 3. セカンドライフ由来データは出所を識別する

名前・ラベルだけに依存せず、生成元を示すメタデータを持たせる。

ライフイベントでは `LifeEventEntry.source` を使用する。

- `second_life_housing`: セカンドライフ住まい設計から生成
- `second_life_nursing`: セカンドライフ介護設計から生成

既存保存データとの互換性のため、旧ラベルも移行判定に使用する。

### 4. 連動データは通常入力と同じ操作をさせない

セカンドライフ由来の projection は、通常の手入力データと同じように編集・削除・家族間コピーしない。

変更したい場合は `SecondLifeState` 側の設計を変更し、projection を再反映する。

これにより、設計本体と計算用データの食い違いを防ぐ。

### 5. 「設計済み」と「反映済み」を区別する

セカンドライフ画面では、設計そのものが存在するかだけでなく、各ドメインへ同じ内容が反映されているかを確認できるようにする。

状態の考え方:

- 設計なし
- 設計あり・未反映
- 設計あり・反映済み
- 設計変更後・再反映が必要

## 現在の実装範囲

### 介護

`SecondLifeState.nursingByTarget` を設計本体とする。

ライフイベントに生成される介護費は `source: 'second_life_nursing'` を持つ計算用 projection とし、ライフイベント画面では読み取り専用で表示する。

家族間の「設定をコピー」ではこの projection をコピーしない。

### 住まい

セカンドライフの住まいシナリオを設計本体とし、転居時は既存住まいとの期間整合性を確認する。

リフォーム一時金としてライフイベントへ生成するデータには `source: 'second_life_housing'` を付ける。

物件そのものの source メタデータ整理は後続フェーズで行う。

### 生活費

セカンドライフの生活水準を設計本体として、生活費スケジュールへ反映する。

現在は生活費スケジュール側に source メタデータがないため、後続フェーズで整理する。

## 後続フェーズ

1. 反映操作をできるだけ Q12 セカンドライフ側へ集約する
2. 住まいの生成物件に source / linked-design 情報を持たせる
3. 生活費の生成スケジュールに source / linked-design 情報を持たせる
4. 地元へ戻り実家をリフォームする場合の「住まい実体」と「一時金」を一貫したモデルにする
5. 住まい・生活費・介護それぞれに独立した「未反映 / 反映済み / 再反映必要」状態を持たせる

## 禁止事項

- ラベル文字列だけを唯一の識別子として新規実装する
- セカンドライフ由来の projection を通常入力のコピー対象に含める
- projection 側を編集して `SecondLifeState` と別の値を持たせる
- 「入力済み」の判定を projection の存在だけで行い、設計本体を無視する
